# repositories

Data-access layer over the SQLAlchemy models. Services depend on
repositories for persistence; the API layer never touches SQLAlchemy
models directly.

Repository methods are persistence-only: no HTTP exceptions, no AI logic.
`create`/`update`/`delete` flush the session (so autogenerated IDs and
`onupdate` timestamps are available to the caller) but never commit —
committing is owned by the service layer.

Implemented:

- `project.py` — `ProjectRepository`: `create`, `list`, `get_by_id`,
  `update`, `delete`.
- `evidence.py` — `EvidenceRepository`: `create_for_project`,
  `list_for_project`, `get_by_id`, `update`, `delete`.
- `persona.py` — `PersonaRepository`: `create_batch_for_project`,
  `list_for_project`, `get_by_id`, `delete`.
- `experiment.py` — `ExperimentRepository`: `create_with_variants_and_personas`,
  `list_for_project`, `get_by_project_and_id`, `get_persona_ids` (reads the
  raw `experiment_personas` association rows, distinct from the
  ORM-joined `experiment.personas`, so a since-deleted persona can be
  detected at execution time), `update`, `update_status`, `delete`.
- `simulation_run.py` — `SimulationRunRepository`: `create_completed`,
  `create_failed`, `list_for_experiment`, `get_by_experiment_and_id`. Each
  run is created independently — `ExperimentExecutionService` commits after
  every single run, not the repository.
- `insight.py` — `InsightRepository`: `create_batch_for_experiment`,
  `list_for_experiment`, `exists_for_experiment`.
- `decision_memo.py` — `DecisionMemoRepository`: `create_for_experiment`,
  `get_for_experiment` (at most one row per experiment).
- `human_feedback.py` — `HumanFeedbackRepository`: `create_for_experiment`,
  `list_for_experiment` (stable order by `session_date`, `created_at`,
  `id`), `get_by_experiment_and_id`, `update`, `delete`.
